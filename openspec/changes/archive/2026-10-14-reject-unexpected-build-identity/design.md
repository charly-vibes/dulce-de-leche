# Design: Reject release artifacts from an unexpected publisher or build identity

## Trust roots

The trust root for ddl release artifacts is **ddl's own release workflow**:

- `repository: charly-vibes/dulce-de-leche` — constant `EXPECTED_PROVENANCE_REPOSITORY`
- `workflow: Release` — constant `EXPECTED_PROVENANCE_WORKFLOW` (matches
  `.github/workflows/release.yml`)

The release tag is not a static root: it is parsed from the archive URL
(`…/releases/download/<tag>/<asset>`) and checked against the manifest, so a manifest
describing a *different* release's build is rejected even if it names the correct
repository and workflow. Provenance manifests are fetched over TLS (HTTPS via reqwest
rustls) from the same release as the asset.

### Residual limitation (documented, not hidden)

The manifest is published by the same release it describes; an attacker with write
access to *this repository's releases* could substitute both. The identity check
defends against artifacts published under a *different* repository, workflow, or tag
(forked workflows, re-published tags, mirrored releases) — a strictly stronger
posture than the checksum-only baseline, at zero new dependencies. Full defense
against repository compromise is sigstore-style attestation (below).

## Verifier dependency: explicit design justification

**Decision: no new dependency.** Candidate verifiers considered:

- **`sigstore-rs`** (Sigstore/Rekor verification) — rejected: heavyweight
  (certificate-chain + transparency-log infrastructure), large dependency tree
  (conflicts with the no-lockfile-churn constraint), and the release workflow does not
  yet produce Sigstore attestations. Selected *only if* a follow-up adds
  `actions/attest-build-provenance` to the release workflow; that follow-up must
  re-run this design justification (per the ticket's dependency rule).
- **GitHub API attestation endpoint** — rejected: requires API rate budget and token
  handling in the hot install path, and couples ddl to a single attestation API
  shape.
- **Chosen: self-published `provenance.json`** — a small JSON manifest generated by
  the release workflow, parsed with the already-pinned `serde_json`, fetched with the
  already-pinned `reqwest`, digested with the already-pinned `sha2`. It carries the
  three identity fields the ticket requires (repository/workflow/tag) plus per-asset
  digests, and the failure modes (missing, malformed, transport-failed, contradicting)
  map onto the DDL-yts rejection plumbing already in place.

## Legacy transition

`DDL_ALLOW_UNVERIFIED_RELEASE=1` remains the single explicit authorization knob. It
bridges only *absence* of verification (no checksum, no provenance, tag-less URL).
It never rescues a *contradiction*: a manifest naming the wrong repository, wrong
workflow, wrong tag, or listing a digest that does not match the downloaded bytes is
rejected unconditionally. This preserves the DDL-yts invariant that explicit
authorization covers "verification unavailable", never "verification failed".

## Policy placement

`enforce_provenance_policy` is pure (no network, no filesystem), mirroring
`enforce_checksum_policy`, so all five negative fixtures run without connectivity and
without touching live releases or credentials. The networked lookup
(`fetch_provenance`) only classifies retrieval outcomes into `ProvenanceLookup`;
rejection decisions live in the policy. Rejection reuses `ChecksumUnavailable`
(availability/identity violations) and `ChecksumMismatch` (altered bytes), so no
destination mutation can occur on the error paths — `install_binary` extracts only
after `verify_download` returns `Ok`.

## Test fixture policy

All fixtures are byte slices and constructed manifests in `tests/install_policy.rs`.
No production credentials, no live releases, no network access.
